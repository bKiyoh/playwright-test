# GitHub Copilotのトークン消費を抑えながら、苦手なことを任せる方法を模索する

苦手なものは、できれば避けたい。

とはいえ、仕事ではそうもいきません。

私にとって苦手な工程のひとつが、テスト工程です。

- テストケースを考える
- テスト仕様書を作成する
- テストを実施する

もちろん、テストが重要であることは理解しています。

ただ、重要だとわかっていても苦手なものは苦手です。

苦手意識がある作業は気持ちも下がり、パフォーマンスにも影響します。

そこで思うのが、

**苦手なものを、AIに任せられないか**

ということでした。

幸い、現在のプロジェクトではGitHub Copilotを利用できます。

最初はコミット内容を見てもらい、そこからテストケースを考えてもらう形を試しました。

実際にやってみると、ゼロから自分で考えるよりもかなり負荷が下がりました。

「これからさらに活用して、テスト工程をもっと楽にできないか試行錯誤しよう！」

そう息巻いてたところで、6月になりました。

6月からGitHub Copilotの[料金体系が変更](https://github.blog/news-insights/company-news/github-copilot-is-moving-to-usage-based-billing/)されて、これまでのように気軽に大量の情報を投げる使い方はしづらくなりました。

プロジェクト内でも運用ルールが決まり、今後はトークン消費を意識しながら使う必要が出てきました。

それでも精神衛生上

**苦手なものを、AIに任せる**

ことは諦めたくありません。

今回は、Copilotにテストケースを考えてもらう際に、
**なるべくトークン消費を抑えつつ、必要な情報だけ渡す方法**
について考えて実行してみると案外良さそうだったので、その方法をまとめます。

## Copilotに渡す情報を絞る

今回意識したのは、Copilotに渡す情報をできるだけ少なくすることです。

大まかな流れは次のとおりです。

1. 実装差分を確認する
2. Copilotに必要な差分だけ渡す
3. テスト観点を洗い出してもらう
4. テスト仕様書に転記しやすい表形式で出力してもらう

最初からリポジトリ全体や大きな差分を渡すと、トークン消費が大きくなります。

そのため、まずは差分の概要を確認し、必要なファイルだけに絞ってからCopilotに渡します。

## 方法

今回は個人の開発環境でCopilotを使用していないため、手順の確認にはCodexを使用します。

便宜上、本文ではCopilotと記載しますが、今回の検証ではCodexに回答してもらっています。ご了承ください。

題材としては、[前回の記事](https://github.com/jointcrew/tech-blog/discussions/17)で作成したTodoアプリの[リポジトリ](https://github.com/bKiyoh/playwright-test)を使います。

このTodoアプリに編集機能を追加した際の差分をもとに、テストケースを洗い出す流れを紹介します。

### 1. 変更ファイルを確認する

変更されたファイル名を確認します。

```bash
git diff --name-only 比較元ブランチ...HEAD
```

結果は修正したファイルが一覧として出てきました。

```bash
src/App.vue
src/styles.css
```

### 2. 必要なファイルだけ差分を出力する

変更ファイルの中から、テストケースに関係しそうなファイルだけを指定して差分を出力します。

```bash
git diff --unified=3 --output=e2e-diff.txt master...HEAD -- src/App.vue src/styles.css
```

実行すると、差分をまとめたテキストが作成されました。

<img width="555" height="632" alt="Image" src="https://github.com/user-attachments/assets/3daaaebc-eb7f-4dd0-8eb1-d5d233b1d10f" />

これで、Copilotに渡す情報を選定できました。

### 3. Copilotに依頼する

実際にCopilotへ依頼する場合は、次のようなプロンプトを使いました。

```text
下記の要件で、E2Eテストで確認すべきシナリオを洗い出してください。

条件:
- 差分から判断できる内容だけを対象にする
- 既存仕様の推測はしない
- 推測が必要なものは「要確認」と書く
- 重要度の高い順に、必要なシナリオを過不足なく出す
- 正常系を優先する
- 必要であれば異常系も含める
- 余計な説明は不要
- 出力は以下のMarkdown表形式にする

出力形式:
| No | テスト観点 | 前提条件 | 操作 | 期待結果 | 備考 |

差分:
// 先ほど出力した `e2e-diff.txt` の内容を貼り付けます。
```

結果、以下のような内容が返ってきました。
| No | テスト観点 | 前提条件 | 操作 | 期待結果 | 備考 |
|---:|---|---|---|---|---|
| 1 | Todoを編集開始できる | Todoが1件表示されている | 対象Todoの「編集」ボタンを押す | 対象Todoが編集モードになり、入力欄・保存ボタン・キャンセルボタンが表示される | 正常系 |
| 2 | 編集内容を保存できる | Todoが1件編集モードになっている | 入力欄の値を変更し、保存ボタンを押す | Todoタイトルが変更後の文字列になり、編集モードが終了する | 正常系 |
| 3 | Enterで編集内容を保存できる | Todoが1件編集モードになっている | 入力欄の値を変更し、Enterを押す | Todoタイトルが変更後の文字列になり、編集モードが終了する | 正常系 |
| 4 | 編集をキャンセルできる | Todoが1件編集モードになっている | 入力欄の値を変更し、キャンセルボタンを押す | Todoタイトルは変更前のままで、編集モードが終了する | 正常系 |
| 5 | Escで編集をキャンセルできる | Todoが1件編集モードになっている | 入力欄の値を変更し、Escを押す | Todoタイトルは変更前のままで、編集モードが終了する | 正常系 |
| 6 | 空文字・空白のみは保存できない | Todoが1件編集モードになっている | 入力欄を空文字または空白のみにする | 保存ボタンが無効になる | 異常系 |
| 7 | 空文字・空白のみで保存処理してもタイトルは変更されない | Todoが1件編集モードになっている | 入力欄を空文字または空白のみにし、Enterを押す | Todoタイトルは保存されず、編集モードが継続する | 異常系 |
| 8 | 編集中のTodoを削除すると編集状態が解除される | Todoが1件編集モードになっている | 対象Todoの削除ボタンを押す | 対象Todoが削除され、編集入力欄が表示されない | 正常系 |
| 9 | 編集中に全削除すると編集状態が解除される | Todoが1件以上あり、いずれかが編集モードになっている | 全削除ボタンを押す | Todoが全て削除され、編集入力欄が表示されない | 正常系 |
| 10 | 編集中の完了済みTodoで入力欄に取り消し線が付かない | 完了済みTodoが1件表示されている | 対象Todoの編集ボタンを押す | 編集フォームは通常表示になり、完了済みタイトル用の取り消し線が入力欄に適用されない | CSS差分由来 |
| 11 | 編集フォームがTodoタイトル領域の幅いっぱいに表示される | Todoが1件編集モードになっている | なし | 編集フォームの幅がタイトル領域に対して不足しない | CSS差分由来。要確認 |

これでテストケースの洗い出しが完了です。

普段の業務なら、ここから過不足の検討をしていきます。

## トークン消費を抑えるために意識したこと

今回意識したのは、次の点です。

- リポジトリ全体を渡さない
- `git diff --name-only` で対象ファイルを絞る
- テストに関係しそうなファイルだけ差分を渡す
- 出力形式を最初から指定する

極論を言うとCopilotに「全部見て考えて」と依頼すると楽ではあります。

ただ、その分トークン消費も大きくなります。

必要な情報だけを渡し、回答の形式も指定することで、比較的少ない情報量でも使いやすい結果を得られました。

## 注意点

AIが出してくれるテストケースは、あくまでたたき台です。

実装差分から読み取れる内容には限界があり、仕様書や画面仕様、既存の挙動までは正確に判断できない場合があります。

そのため、出力された内容はそのまま使うのではなく、実際の仕様と合っているか、E2Eテストで確認すべき観点として適切かは人間側で確認する必要があります。

AIに任せるというより、**ゼロから考える負担を減らすために使う**という感覚が近いです。

## 終わりに

まだ私自身も模索中なので、今回の方法が確実に効果的だとは言い切れません。

ただ、AIに渡す情報を絞れば、AI側の負担を減らせます。

その結果として、トークン消費を抑えることにもつながるのではないかと考えています。

もちろん、差分を確認したり、渡す情報を整理したりする分、こちら側の手間は少し増えます。

それでも、AIがなかった頃に比べればかなり楽です。

むしろ、必要な情報だけを渡すことで精度が上がるなら、その手間は十分に許容できると感じています。

けれど、それでもやっぱり苦手なものは丸投げしたい欲は消えることはありません。
